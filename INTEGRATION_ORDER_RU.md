## Порядок действий

В локальном Git checkout на собственной ветке распаковать ZIP **поверх репозитория**, не удаляя существующие файлы:

```bash
git switch chapter6-ophthalmology
python install_fuzzyxai_upgrade.py --check
python install_fuzzyxai_upgrade.py
python install_fuzzyxai_upgrade.py --check
python -m pip install -e '.[dev]'
python -m pytest -q tests/test_doctoral_*.py tests/test_release_transactional_installer.py
python -m pytest -q tests/test_chapter5_*.py
python -m experiments.doctoral_native_repeated --out reports/chapter5/native_fuzzy_repeated
python -m pytest -q
git status --short
```

Установщик проверяет **все восемь** исходных модификаций до первой записи; при ошибке записи выполняет откат. Повторный вызов безопасен. Старые `apply_doctoral_upgrade.py` и `apply_ch5_practice.py` оставлены для совместимости, но **запускать их перед общим установщиком не требуется**.

Перед pull request необходимо проверить **весь** исходный набор тестов. GitHub-подключение в этой сессии read-only для создания веток (`HTTP 403`), поэтому коммит и PR **не созданы**. При изменённом содержимом исходных модулей установщик останавливается, а не перетирает чужие правки. Для публикации проекта требуются работающие Git-права.

## Проверка научных границ

- Исходный WDBC: обучаются реальные термы/правила и реальная логистическая модель на их активациях, без обучения на тесте.
- `Γ` проверяется через независимый арифметический пересчёт из правил и должен быть почти нулевым **по конструкции**. Это не независимая экспертиза истинности объяснения.
- `Δ` измеряет изменение вероятности после удаления части правил. Часть случаев намеренно получает `invalid`, если превышен предел `0.15`.
- Нельзя публиковать метрики WDBC как доказательство клинической эффективности или как результаты ЭКГ. PTB-XL исходные записи не обработаны.
- Структурный сертификат может иметь `valid` при неверном прогнозе; проверка качества исходного предиктора является отдельной задачей.
- Введение и главы 1–4 DOCX вообще не меняются.
